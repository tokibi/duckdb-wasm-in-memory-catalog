# コンセプト

In-Memory Catalog の設計思想と、内部でどのようにデータとキャッシュが管理されているかを解説します。

---

## 1. カタログモデル

インメモリカタログは、ホストアプリケーションが管理するデータモデルを、DuckDB の読み取り専用カタログとしてそのまま公開する仕組みです。

![Browser、Worker、remote file の構成](./assets/in-memory-catalog-worker-architecture-overview.svg)

### スレッドの分離と同期アクセス
- **メインスレッド**: カタログコントローラーと DuckDB クライアントが動作します。
- **Dedicated Worker**: DuckDB-Wasm とカタログメタデータストアが同じ Worker 内で動作します。
- **同期的なメタデータ解決**: DuckDB のクエリ実行エンジンがテーブルを探索する際、同一 Worker 内のメタデータストアへ直接アクセスすることで、非同期通信によるオーバーヘッドやクエリスケジューラのブロッキングを防ぎます。
- **定義権限**: カタログの定義権限は常にアプリケーションにあります。DuckDB はそのメタデータを読み取り専用ビューとして消費します。

---

## 2. カタログの更新ライフサイクル

カタログの更新には、2つの方法が用意されています：

| メソッド | 対象 | 用途 |
|---|---|---|
| `publishSnapshot()` | カタログ全体 | スキーマ構成や全テーブルの刷新、初回セットアップ時 |
| `replaceTable()` / `replaceView()` | 単一テーブルまたはビュー | 特定テーブルのファイル更新やスキーマ変更。他テーブルは維持 |

### アトミック性と検証
1. **直列化キュー**: コントローラーへの呼び出しはキューイングされ、呼び出し順に Worker へ送信されます。
2. **事前検証**: Worker は新しいスナップショットを受け取ると、構文や列定義の妥当性を検証します。
3. **アトミックな差し替え**: 検証に成功した場合のみカタログ状態が更新されます。検証に失敗した場合は変更が破棄され、既存のカタログ状態が維持されます。
4. **内部世代カウンタ**: Worker は更新成功ごとに内部カウンタを進め、DuckDB 側のテーブルエントリや View バインドのキャッシュを無効化します。

---

## 3. テーブル定義の関心事の分離

本ライブラリでは、テーブル定義を以下の3つの独立した関心事として整理しています：

```text
1. columns   (DuckDB からどう見えるか) -> 列名、データ型、NULL許容性
2. scanner   (ファイルをどう解釈するか) -> Parquet / CSV / JSON / XLSX とそのオプション
3. files     (ファイルがどこにあるか)   -> リモートまたはローカルの URI リスト
```

### スキャナの明示指定
.parquet や .csv などの拡張子からスキャナを自動推論することはしません。すべてのテーブルで `scanner: { type: '...' }` を明示します。これにより、URL が拡張子を持たない動的エンドポイントであっても決定論的にパースされます。

## 4. テーブルスナップショットとキャッシュ分離

### キャッシュ分離の背景
DuckDB-Wasm はブラウザ内で動作するため、HTTP Range リクエストの結果や Parquet メタデータを内部でキャッシュします。同じ URL のファイルがバックエンドで更新された場合、DuckDB が古いキャッシュを参照し続けてしまう問題があります。

### URL フラグメントによる解決
In-Memory Catalog では、各テーブルに `snapshot` 識別子としてバージョン文字列やハッシュ値を設定します。

```text
アプリケーションが指定した URI:
  https://example.com/data/sales.parquet

DuckDB-Wasm 内部で使用されるスキャン URI:
  https://example.com/data/sales.parquet#duckdb-snapshot=sales-20260925
```

- **HTTP への影響**: URL フラグメントはブラウザの仕様上 HTTP リクエストヘッダーやネットワーク通信には送信されません。Web サーバーや CDN から見れば元の URL のままです。
- **DuckDB キャッシュの更新**: DuckDB の内部キャッシュキーはフラグメントを含む完全な URI を使用するため、`snapshot` 文字列が変わることで古いキャッシュがバイパスされ、最新のデータが読み込まれます。
- **キャッシュの維持**: 他のテーブルが更新されても、`snapshot` が変わっていないテーブルの DuckDB キャッシュは有効なまま残ります。

## 5. SQL ビューのバインドと無効化

スナップショットにはテーブルだけでなく、SQL ビューを含めることができます。

- **遅延バインド**: ビューの列定義や型はスナップショット定義時には不要です。DuckDB がクエリ実行時に初めて `query` 文字列を解析して列情報を導出します。
- **自動無効化**: 参照先のテーブルが `replaceTable` や `publishSnapshot` で更新された場合、カタログ世代カウンタが進むことで、次のクエリ実行時に自動的にビューが再バインドされます。

---

## 6. なぜ読み取り専用なのか

DuckDB 内での `CREATE TABLE`、`ALTER TABLE`、`DROP TABLE` などの DDL や、`INSERT` / `UPDATE` などの DML は拒否されます。

DuckDB 側でのテーブル変更を許可した場合、アプリケーション側のデータモデルと DuckDB 内部のカタログ状態の 2 つの Source of Truth が存在することになり、状態の同期ズレや競合が発生するためです。

状態の更新は常にアプリケーション側で行い、それをスナップショットとしてカタログへ反映する一方向データフローをとることで、データ整合性を保ちます。

---

## 7. ランタイムの所有権

- **ホストアプリケーションの所有**: Dedicated Worker、DuckDB インスタンス、Database 本体のライフサイクル。
- **コントローラーの所有**: カタログ接続、Worker 内のワークスペースセッション、Attach されたカタログ。

`catalog.close()` を呼ぶと、カタログの Detach とスナップショットの破棄が行われますが、DuckDB Worker 自体は終了しません。複数のカタログを切り替えたり、DuckDB を継続して別の用途に使うことができます。

---

## 8. Lakehouse format との関係

Apache Iceberg や Delta Lake などの Lakehouse format が利用できる環境であれば、ストレージ側でメタデータや履歴を管理できるそれらの形式を採用する方が適しています。

本ライブラリの目的は、ストレージ側にそうした専用フォーマットや管理基盤が存在しない場合でも、スキーマ定義、列情報、ファイル URL リストといった、アプリケーションがメモリ上に持つ軽量なデータ構造をそのまま table や view の定義として DuckDB-Wasm に公開し、クエリ可能にすることです。
